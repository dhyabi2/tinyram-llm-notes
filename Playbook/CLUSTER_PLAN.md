# Cluster plan (low budget): does adding a node double tok/s?

 Model: tools/cluster_model.py in the public repo. All tok/s are estimates; prices are listing prices seen 2026-10-29.

## Answer

VERDICT. Under a few hundred dollars, "add one node = double" is NOT reliably achievable. It is achievable only for the first added node, and only under two conditions at once. (1) The base node is I/O-bound, meaning 8 GB (maybe 16 GB) of RAM, so that the second node's RAM pools the expert cache and the hit rate rises from about 0.77 to about 0.97. (2) The dense part (57% of FLOPs: attention, router, shared tensors) is also split across nodes, with a replicated router and 2 small all-to-all exchanges per layer (96 per token). No such code exists in llama.cpp today. Its RPC backend is a layer split, which does not speed up a single stream. That software has to be written.

Audited model (16 GB nodes, 55 GFLOP/s, real-model hit curve):
- With the dense part on one master, tok/s saturates at about 4.1 -> 4.9 -> 5.0 -> 5.0 for 1/2/4/6 nodes. This is Amdahl on the 124 ms of dense compute plus an expert straggler of 1.24 / 1.67 / 2.4 at 2 / 4 / 8 nodes. Experts alone do not scale.
- With both the experts and the dense part split, 2.5GbE gives 4.1 / 6.2 / 9.5 / 11.2 for 1/2/4/6 nodes. 1GbE gives 4.1 / 6.1 / 8.8 / 9.8. 10GbE gives 4.1 / 6.6 / 10.5 / 12.9. The second node is about 1.5-1.6x. Then it flattens: node 3 adds about 1.3x and node 4 about 1.2x. The 6-8 node plateau is 12-14 tok/s.
- A very low-latency fabric (RDMA over Thunderbolt 5) reaches 16 at 8 nodes, but it needs M4 Pro-class Macs costing over $1,000 each. That is out of budget.

What stops it, in order:
1. The expert straggler. Each layer waits for the busiest node.
2. 48 round trips. 96 exchanges x latency = 18 ms at 0.15 ms RTT and 36 ms at 0.3 ms RTT, a fixed floor that does not shrink with N. Barrier jitter (a wait for the slowest of N nodes at every sync) is not in the model and can double it.
3. Disk I/O vanishes once the pooled cache is above about 60% of experts, so the early "superlinear" gain is one-time.
4. Tensor-parallel efficiency: tp_eff 0.85 is an estimate. The KV-head count (unknown for the 125B) probably limits you to 2, 4 or 8 nodes.

Conflicts resolved by recomputation:
- Lens 1 said 8 GB nodes give 2.0x at 2 nodes and 4.0x at 4 nodes (9.85 tok/s). I recomputed 4 nodes as compute (31 + 39 ms from the 1.67 straggler, divided by 0.85 efficiency, about 82 ms) plus 36 ms of network plus a few ms of I/O. That is about 125 ms, or 8 tok/s. So that lens was about 20-25% optimistic, because it used the old constant 1.27 straggler, perfect tensor-parallel efficiency and the 30B hit curve. The audited numbers are used throughout.
- Straggler: the placement lens showed that replicating the hottest 25% of experts on every node cuts the 4-node straggler from about 1.67 to 1.14 (30B proxy, 128 experts), worth about +15-20% on its own. I could not confirm this for 512 experts, so it is a possible upside, not in the table.
- Per-node GFLOP/s differ by hardware agent: a 6-core x86 micro PC is about 72-75, an N305 about 60 (Gracemont, guessed), an N100 about 27-34. None is measured, so the first experiment is to measure it.
- Single-node anchors: the overlap=ideal model gives 4.58, but we project 2.2-2.5 at 8 GB, 3-4 at 16 GB, 4.3 at 32 GB. I use the projections as the single-node base and the audited ratios for scaling, then apply a 25-40% haircut for jitter and a non-ideal split.
- Unresolved: real 125B hit rate, router popularity skew, USB-NIC RTT (estimated 0.2-0.5 ms) and the Gracemont GFLOP/s. All are unmeasured. The 2-node ping-pong test below decides most of this.

Honest alternative: one rented 128 GB dedicated box (EUR 41-48/month, from a tracker and community posts, unverified) would hold the whole model in RAM. It is estimated at 6-8 tok/s with no cluster. Below about 4-5 owned nodes it beats any cheap cluster on speed per dollar. Also, one 32 GB node (4.3 tok/s projected) beats most of the pipeline options below.

BEST BUDGET PLAN: use the Mac we own plus ONE cheap used 16 GB 6-core micro PC (about $230 plus a $25-45 2.5GbE USB adapter). Get a 5-port switch (about $50-80) only if you go to 3 or more nodes. Measure the network first. If p99 barrier latency is under about 0.3 ms, build the split dense + expert design. Expect about 5-6 tok/s at 2 nodes, up from 3-4. If it is not, buy a 32 GB machine or rent one.

## Does adding a node double speed?

Only for the first added node, and only if two things are true. First, the base node is I/O-bound (8 GB RAM, maybe 16 GB), so the extra RAM pools the expert cache. Second, the dense part is also split across nodes with custom tensor-parallel code. In the audited model the second node then gives 1.5-1.6x at 16 GB (4.1 -> 6.2-6.6) and about 2x at 8 GB or on a slow disk. The third node gives about 1.3x and the fourth about 1.2x. The plateau at 6-8 nodes is about 12-14 tok/s.

Without the dense split it is about 1.1-1.2x. Pipeline or layer split (llama.cpp RPC) is about 1.0-1.1x at 16 GB, because the 218 ms of compute per token stays serial.

Three limits:
- Amdahl on the dense 57%.
- 96 exchanges x latency per token, a fixed 18-36 ms.
- Aggregate RAM: 69 GB needs about 5 nodes of 16 GB to be fully resident, and the cache benefit ends by then.

Linear scaling beyond 2 nodes is not realistic on cheap Ethernet.

## Software that has to be built

Yes for every option that scales. Stock llama.cpp RPC is a layer split and gives about 1.0-1.1x. Scaling needs a custom runtime with 4 parts:
- A replicated router.
- Tensor-parallel attention and shared-tensor slices.
- Expert sharding by expert id, with each node reading its own shard from its own disk.
- A busy-polling TCP_NODELAY (or UDP) exchange of about 4 KB, twice per layer.

Only option 3 below, the pooled-cache layer split, needs just the existing RPC plus the read pool.

Do not build before measuring. Step 1 needs no model: a 4 KB ping-pong between the Mac and the PC, and an emulation of 96 barriers per token.

## Ranked options

### 1. 2-4 used 16 GB 6-core micro PCs, 2.5GbE, expert-parallel + tensor-parallel dense (best-value scaling build)

Totals: 1 node about $255, 2 nodes about $570, 4 nodes about $1,080, 6 nodes about $1,590. Own Mac plus one PC about $255-300 (adapters for both, no switch, direct cable if the Mac has an adapter). Asking prices, not confirmed sold prices.
- tok/s at 1/2/4/6 nodes: Hardware agent model at 75 GFLOP/s, 2.5GbE, expert + dense split: 3.81 / 7.55 / 14.28 / 18.69 (upper bound, 0.2 ms RTT). My audited ratios on 16 GB nodes give 2 nodes 1.5-1.6x, 4 nodes 2.3x, 6 nodes 2.7x. With a 25-40% haircut for jitter and a non-ideal split, plan on about 3.5 / 5.5-6 / 8-10 / 10-13 (estimate, unmeasured). Expert-only with a master on dense: 3.81 / 5.99 / 7.87 / 8.46 (model), realistically 3.5 / 4.5 / 5 / 5.
- build: Used Dell OptiPlex 7080 Micro (i5-10500T/10600T, 16 GB DDR4, M.2 NVMe at about 3 GB/s) or an equivalent ThinkCentre Tiny / EliteDesk Mini, or a Ryzen 5 5600U/H mini PC. Each node gets a $23-45 USB 2.5GbE adapter and a 5-port 2.5GbE switch. Each node holds 69/n GB of experts on its own NVMe plus a slice of the dense weights. Custom runtime as in must_build_software. Our Mac can be one of the nodes (give it a proportional share by measured GFLOP/s).
- why it scales: It is the only design that shrinks compute per node (both dense and expert FLOPs divide by n) and also pools cache and disk bandwidth (the 69 GB model is 17 GB per node at 4 nodes, nearly RAM-resident). The 4 KB activations make bandwidth irrelevant, so ordinary 2.5GbE is enough if latency holds.
- what stops it: 96 exchanges x per-message latency (36 ms at 0.3 ms RTT, 18 ms at 0.15 ms), plus the expert straggler (1.24 at 2 nodes, 1.67 at 4, uniform placement) and barrier jitter. From node 3 on, each node adds only 1.2-1.3x, so 4 nodes is the sweet spot and beyond that the money is wasted. The 6-core Comet Lake 35 W T-series part may throttle, so sustained GFLOP/s may be below 72.
- risks: Custom code needed (weeks of work). USB NIC RTT may be 0.3-0.5 ms, which would cut the 4-node figure by 25-40%. The 125B hidden size and head count are unknown, so n must divide the KV heads (2/4/8 safe, 3/6 not). Some Micro models do not have a second usable M.2 slot (not needed here). Used prices vary a lot. Prices are asking prices.
- first experiments: 1) On the Mac plus the PC (direct cable or the switch): 4 KB ping-pong with busy-polling TCP_NODELAY sockets, 100k reps, record p50/p99/p99.9, then emulate 96 barriers interleaved with a 1 ms/n spin and measure the stall per token. Pass if p99 under 0.3 ms and stall under 2 ms for 2 nodes; kill if the 2-node stall exceeds the saved compute. 2) Run a Q4 matvec benchmark on the actual PC (GFLOP/s) and fio with 2-3 MB reads. Plug both into the audited model (cluster_model.py with the real-hit curve). 3) Replay a routing trace to compute the real straggler and the hot-25% replica gain on 512 experts. 4) Two-node mock: split heads of the 30B proxy over the Mac and the PC and compare against the model's 1.5-1.6x.

### 2. 4 cheap Intel N305 (or N100) mini PCs with built-in 2.5GbE (cheapest per tok/s, weakest per node)

- tok/s at 1/2/4/6 nodes: Hardware agent (N305, 60 GFLOP/s): 2.47 / 5.7 / 11.8 / 15.9 with dense split, and 2.47 / 4.5 / 6.3 / 6.8 expert-only. Audit (N100, 27.5 GFLOP/s, 1 GB/s disk, 2.5GbE): 1.72 / 3.17 / 5.21 / 6.30 with dense split. The two GFLOP/s guesses differ, so I could not resolve it. Planning band after haircut: N305 about 2.3 / 4-4.5 / 7-9 / 9-11, N100 about 1.7 / 3 / 4.5-5 / 5.5-6 (estimates).
- build: N305 8-core mini PCs (about 60 GFLOP/s est.) with 16 GB SO-DIMM, an M.2 SSD and dual 2.5GbE (i226), joined by a $30-50 unmanaged 2.5GbE switch. Same custom runtime as option 1. Compute-bound, so network latency matters less than for faster nodes, which is why relative scaling is good: 3.0x at 4 nodes on 2.5GbE for N100.
- why it scales: Low GFLOP/s makes each layer's compute large (about 9 ms on 1 node, 2-3 ms at 4), so the fixed network cost is a smaller share of the token. Pooled RAM turns a 16 GB node into a nearly all-resident cluster at 4 nodes.
- what stops it: Per-node compute and single-channel DRAM (38 GB/s spec; about 15 GB/s effective on our 4-core Mac), M.2 slots wired at PCIe x1-x2 (about 1.5 GB/s, assumed), and the same latency, straggler and KV-head limits as option 1. Absolute speed stays low (under 10 tok/s at 4 nodes).
- risks: Quality of cheap no-name boxes varies widely. 16 GB cap per node. AVX2 4-bit kernels on Gracemont may run below the guessed 2.5 FLOP/cycle. Custom code needed.
- first experiments: Buy one N305 box. Measure the matvec GFLOP/s, the DRAM streaming rate and the NVMe rate, then put them into the model. Run the same ping-pong test between it and the Mac. Do not buy a second one unless GFLOP/s is at least 50 and the 2-node barrier stall is under 2 ms.

### 3. Pooled-cache layer split on 8 GB nodes with the existing read pool and llama.cpp RPC (stock-software option, one-time gain)
- cost: Used M1 Mac mini 8 GB/256 GB $225-330 (forum sales $225-275 shipped in Apr-May 2026 at fredmiranda.com/forum/topic/1940908; refurb.me lowest refurbished $315, last seen early Aug 2026; page seen 2026-10-29). A 16 GB PC at about $230 is an alternative. 2 nodes about $450-650 including our own Mac as node 1, about $250-330 if the Mac is node 1. A single 32 GB node gives about the same without a cluster.
- tok/s at 1/2/4/6 nodes: 8 GB nodes, model with the 30B-trace hit curve (optimistic), serial: 2.48 / 3.66 / 4.26 / 4.25. Audit window mode with the real-hit curve gives somewhat less (about 4.3 plateau). 16 GB nodes: 4.11 / 4.54 / 4.57 / 4.57 (window), 3.14 / 3.94 / 4.36 / 4.35 (serial), i.e. 1.1-1.4x at best. Slow disk case: 0.73 / 1.80 / 3.15 / 3.15 (8 GB, 0.5 GB/s SATA).
- build: 2-3 used or existing 8 GB, 4-core machines, each running the read pool on its own layer range, linked by plain 1GbE (4 KB per hop, so latency barely matters). Needs only a check that the cache pools across the node boundary. No tensor-parallel code.
- why it scales: It does not scale. It removes disk misses once, which is a 1.5-4x gain only if the start is disk-starved.
- what stops it: Sequential layers: the ceiling is 218 ms of compute per token, so 4.58 tok/s. Nodes beyond 2-3 add nothing.
- risks: Low risk and low gain. Our own earlier tests showed 1.0-1.11x when the start node already had 16 GB. Cache pooling across RPC is not verified. Cheaper to buy RAM for one machine than a second node.
- first experiments: Run the 30B proxy on one 8 GB node, then split layers over 2 nodes over 1GbE with a plain activation relay. Log hit rate and time per token. Pass if 2 nodes reach 1.4x or more over 1 node. Compare with the price of a single 32 GB machine.

- tok/s at 1/2/4/6 nodes: Hardware agent: with 10GbE at 75 GFLOP/s, 3.81 / 8.3 / 17.1 / 23.8. Audit, 16 GB, 55 GFLOP/s: 10GbE 4.1 / 6.6 / 10.5 / 12.9; Thunderbolt bridge 10.1 at 4 nodes; RDMA-class 11.3 at 4 nodes. Compared with option 1 the gain is +20% at 2 nodes, +37% at 4 and +54% at 6, at 3x the cost.
- build: Small-form-factor or tower used PCs with a free PCIe x8 slot (a Micro/Tiny box has none). Each gets a Mellanox ConnectX-3 NIC, a direct DAC cable for 2 nodes, or a small 10GbE switch for 4. Transport is verbs or busy-polling, with an isolated core and IRQs moved off it, aiming at 20-50 us per barrier instead of 150-300 us.

- what stops it: Straggler, the dense Amdahl residual, tensor-parallel efficiency and the KV-head limit. At 4 nodes the wire is no longer the limit, compute is.
- risks: Linux-only engineering, with interrupt coalescing, isolcpus and busy polling all to be tuned. No source measures ConnectX-3 RTT for LLM decode. Not worth buying until option 1's ping-pong shows the wire is the wall.
- first experiments: Before buying anything, measure busy-polling against blocking sockets between the Mac and the PC. If busy polling alone already brings p50 to under 60 us, skip the NICs.

### 6. Lossless speculative verification layered on option 1 (an add-on, not a scaling method)
- cost: $0 extra hardware. A draft model needs about 0.6 GB of RAM. Full-copy nodes need a 69 GB SSD each (about $40-70 per 256-512 GB, estimate).
- tok/s at 1/2/4/6 nodes: Added on top of option 1 on gigabit: +10-25% only if acceptance is 0.7-0.8 (4.6 / 6.3 / 10.3 / 13.1 -> 5.2 / 7.6 / 12.1 / 15.2 at a=0.8, gain mostly from amortising latency). Position-parallel replicas at a=0.7: 3.05 / 4.5 / 6.2 / 6.9; at a=0.3 flat 3.4. Geometric cap 1/(1-a): 3.3 tokens at a=0.7. At 10GbE speculation adds at most +5%. Not credible without a good drafter: our own n-gram acceptance measured only 0.11-0.16 on prose and code.
- build: A draft source on node 0 (a small same-tokenizer model or the model's own multi-token head, if the 125B has one). Verify k=4 tokens per pass so the 96 exchanges and the expert reads are paid once per pass. Alternative: position-parallel verification, one draft position per node, exchanging only K/V per layer, with each node holding a full copy of the model on disk.
- why it scales: It does not scale with nodes. It reduces the number of times the latency floor is paid, so it only helps when the network is the weak link.
- what stops it: Compute-bound CPU (verifying k tokens costs about k tokens of FLOPs, with batching gain only 1.3-2.6x), expert-union growth (4 tokens read 1.5-2.7x the expert bytes), and the acceptance rate, which depends on the text.
- risks: Whether a draft model with the 125B tokenizer exists is unknown. On 8 GB nodes the extra expert reads make it worse.
- first experiments: Offline, no cluster: measure acceptance of n-gram lookup and of any small draft against the 30B proxy on 100-200 prompts (chat, code, summarise), at positions 1-4. Go only if acceptance is at least 0.7 on the target workload.

## Skeptic checks

### 2-4 used 16 GB 6-core micro PCs, 2.5GbE, expert-parallel + tensor-parallel dense (best-value scaling build) -> weakened
- corrected tok/s: 1 node ~3.0-3.7 (55 GFLOP/s measured-anchor ~3.1; repo model at 72 GFLOP/s 3.72, but the measured 16 GB 125B projection is 3-4). 2 nodes ~4.0-5.0 (model 6.4 at 0.4 ms RTT and 72 GFLOP/s, about 5.4 at 55 GFLOP/s, less a 20-25% jitter/straggler haircut; x1.3-1.5). 4 nodes ~5.5-7.0 (model 11 at 0.4 ms RTT and 72 GFLOP/s, about 9.4 at 55 GFLOP/s, less the haircut; x1.8-2.0). 6 nodes ~7-8.5 (model 13.5 at 0.4 ms RTT, about 12 at 55 GFLOP/s, less the haircut). The claim's 3.5 / 5.5-6 / 8-10 / 10-13 is too high by about 30-40% at 4 and 6 nodes. All are estimates, unmeasured. Expert-only (master on dense): 3.7 / 5.4-5.6 / 6.3 / 6.8 / 7.3 (model, real-hit, 72 GFLOP/s, 0.3-0.5 ms RTT), realistically 3.1 / 4 / 4.5 / 4.8.
- I reproduced the headline numbers with cluster_model.py using --real-hit --dense-split at 72 GFLOP/s and 0.2 ms RTT. It gives 3.72 / 7.34 / 13.89 / 18.23 for 1/2/4/6 nodes. The claim's 3.81 / 7.55 / 14.28 / 18.69 is the same model at the same optimistic inputs. Those are upper bounds, not a plan.
- 72-75 GFLOP/s is not supported by anything measured. The repo's measured and projected anchor is 55 GFLOP/s, with a 4.58 tok/s compute ceiling. A 35 W T-series i5-10500T/10600T on AVX2 (no VNNI) with DDR4 will likely sustain less than a 4-core M-series Mac. Per token the node must also stream about 3.2 GB of active weights (6B x 4.3 bits) from RAM. That takes about 100 ms at 30 GB/s, so memory bandwidth is a second ceiling that the model ignores. At 55 GFLOP/s the single-node compute term is 218 ms against 167 ms at 72, so every row falls about 25%.
- The 0.2 ms RTT is unrealistic for the stated hardware. A USB 2.5GbE adapter plus a TCP stack plus a switch is typically 0.3-0.5 ms with jitter, and no measurement is cited. The model's network term is 22 ms/token at 0.2 ms RTT, 41 ms at 0.4 ms and 25 ms at 0.5 ms without dense-split. At 0.4 ms RTT the model gives 3.72 / 6.43 / 8.92 / 10.97 / 13.51 for 1/2/3/4/6 nodes, before any haircut. The network term is fixed per token and does not shrink as nodes are added. That is why the curve flattens.
- The dense-split scheme adds 2 extra synchronous messages per layer, so about 96-144 barriers per token, each waiting for the slowest of n nodes. The model uses the mean RTT, not the p99 of an n-way barrier. Jitter from a non-realtime OS, USB interrupts and thermal throttling hits every barrier. The claim's 25-40% haircut is plausible, but it is a guess, and the first experiment is what would decide it.
- The 'dense part is 57% of the compute' result is what makes the 2-node row look good (7.3 vs 5.6 for expert-only). Dense-split, meaning tensor-parallel attention, needs the real model's head and KV-head counts, which are unknown. n=3 and n=6 may not divide the KV heads. Dense-split also needs the KV cache and the sampler to be sharded or replicated correctly. The model counts none of the serial work on the master: router, sampling, norms, embedding and logits. Prefill is not modelled at all. Prefill is compute-heavy and batched and gains little from latency-bound splitting. A 1k-token prompt at 12 GFLOP/token and 50 GFLOP/s is about 4 minutes on one node.
- The 16 GB real-hit single-node figure (3.72 at 72 GFLOP/s) is already above what has been measured. The measured result is 2.8 tok/s on the 30B-A3B proxy, and the projection for 125B at 16 GB is 3-4. The 30B-trace hit curve gives 5.32 for 1 node, which is clearly too optimistic for 125B. The hit rate rises from 0.76 to 0.97 as nodes are added only because the cache pools. That is a legitimate gain, but it rests on an unmeasured assumption that routing on the real model is as skewed as the curve says. Part of the 2- and 4-node speedup is I/O relief (io 102 ms down to 21 and 4 ms), not parallelism. That part is real only if the curve holds.
- Straggler: the model applies a straggler factor of 1.24 at 2 nodes and 1.67 at 4 under uniform placement. A hot-expert replica gain is only proposed in experiment 3. The real value for a given prompt can differ from the average. It also scales badly with n, because top-10 of 512 spread over 4 nodes leaves only about 2.5 active experts per node per layer, so the maximum is dominated by a few unlucky layers.
- The software does not exist. It needs a custom runtime: expert-parallel plus tensor-parallel dense with busy-poll sockets. This is weeks of work with a high risk of landing at 60% of the model. Published CPU clusters for single-stream decode show the same pattern. Distributed Llama (tensor parallel over Ethernet on Raspberry Pis) has a ceiling set by the KV-head count and is very sensitive to the network. One Hackster write-up reports about 3.5 tok/s on a 100 Mbps switch against about 6.06 on 1 Gbps, which is a single data point on a different workload. I found no published batch-1 MoE decode measurement over commodity Ethernet. The expert-parallel (EP) literature I found says the small-message dispatch floor dominates at low batch, and that synchronous layers are bounded by the most loaded device. That points the same way as the stall and straggler terms, but it comes from GPU-cluster papers and is not a CPU/Ethernet measurement. I found no source that confirms the claim and none that fully contradicts it.
- Prices are asking prices from listings that are undated (gotlaptopparts, eBay 336259497002) or old (the 2023 nascompares guide, an AUD price from littlebirdelectronics). The $255-per-node figure carries a switch and an adapter that are not needed for 1-2 nodes. Totals of $570 for 2 nodes and $1,080 for 4 nodes are plausible but unconfirmed. Per added tok/s, the 4th node is poor value: about $510 for +1.5-2 tok/s after the haircut. 'Doubles with each node' is false: even in the optimistic model, 1 to 2 nodes is x2.0 only because of the I/O relief. After that it is x1.4-1.9 for the next two nodes, and about x1.3 per node beyond that.
- Source reading not done in full: I saw only search snippets. I did not open the Distributed Llama README table, so I did not read the 1/2/4/8 node numbers. The only quantitative outside number is the Hackster 100 Mbps vs 1 Gbps result.

Finding: a layer pipeline cannot raise single-stream tok/s by adding nodes once the model is cached. It has one big, one-time gain and then stops. ### placement-routing (graph partitioning / data placement, as in distributed databases)
Bottom line: placement and routing alone cannot double single-stream tok/s. Per-token FLOPs are fixed, and the 57% dense part (about 6.8 of 12 GFLOP) is untouched by where experts live. What placement and routing can do is remove the load imbalance (straggler) that the model understates, and pool caches. Both help most in an expert-parallel layout whose dense part is tensor-parallel (attention split across nodes).

Findings, all model-based and unmeasured on a cluster:
1. The scaling model has an error. cluster_model.py uses a constant straggler of 1.27 for every N. That value is right only for N=2. I simulated 10 random picks over N nodes, which gives straggler 1.25, 1.48, 1.68, 2.07, 2.42 for N=2, 3, 4, 6, 8. Re-run with these, the model's 8-node 'expert' figure drops from 27.8 to 20.2 tok/s (8 GB nodes, fast LAN, overlap, dense split). The 4-node figure drops from 15.1 to 13.1.
2. The best lens-specific fix is lossless. Replicate the hottest 25% of experts per layer on every node, as a read replica in a database. Then assign each hot pick to the least-loaded node. On the Qwen3-30B traces (code, db, story, trained on two and tested on the third), straggler goes from 1.26/1.75/2.53 to 1.02/1.14/1.55 for N=2/4/8, with zero routing change. Hot 25% of experts covers 53% of picks. Adding a small routing cap on the cold remainder gets close to 1.0 at about 1% ppl.
3. Co-activation placement does cluster. Held-out, N=2 has 0.83 of a token's picks on its best single node (random split: 0.63). N=4 has 0.67 (0.43), and N=8 has 0.53 (0.32). But co-activation placement worsens balance: straggler is 1.65, 2.66 and 4.26 for N=2, 4 and 8, against 1.25, 1.73 and 2.57 for random placement. Locality and balance pull against each other. For multi-node throughput, balance matters more.

### redundant-compute (communication-avoiding): replicate what is cheap to replicate, cross the network as rarely as possible
Replication never speeds up the part it replicates, so redundant compute buys fewer or hidden network crossings, not extra FLOPs. The only part with free parallelism is the 43% routed experts, plus (at 8 GB nodes) pooled RAM. Using the repo model (cluster_model.tok_s, real-hit curve, 55 GFLOP/s per node) and my own extension in <scratch> the best realistic result is 8 GB-class nodes with replicated attention and sharded MLP/experts (S1): 2.2 -> about 4.6 (2 nodes) -> 8.6 (4) -> 11 (6) -> 12.4 (8) tok/s. Nothing here keeps doubling past 2-4 nodes. The model's own dense_split number (14.7 at 8 nodes, serial, 8 GB, rtt 0.3) is optimistic: it assumes the 57% dense part scales 1/n and ignores per-layer barrier jitter. ### speculation-across-nodes (branch prediction and speculative execution)
Main finding (model estimates, not measurements): speculation does not by itself make tok/s grow with node count. In a compute-bound CPU cluster a verify pass of k tokens costs about k tokens of compute, and accepted tokens per pass E(k) is below k, so speculation can only recover costs that do not shrink with nodes: the 96 to 192 per-layer messages, the expert-union reads, and idle pipeline stages. The near-linear scaling in the existing model comes from sharding experts plus splitting attention (dense-split). With dense-split on a 10GbE-class link the model gives 4.6 tok/s at 1 node, 7.6 at 2, 14.0 at 4 and 19.6 at 6 with no speculation, which is about linear. Speculation then adds only 0 to 5% at 10GbE. On plain gigabit it adds 15 to 48%, mostly because it amortises latency, and only if the draft is nearly free and accepts well (a >= 0.7 to 0.8). Our own measurement that n-gram acceptance on prose and code is 0.11 to 0.16 (F.md family 21) rules out the free draft for typical text, so a real draft model or an MTP head is required; whether the 125B has an MTP head is unknown. Schemes ranked by value: (1) speculation layered on expert plus dense-split parallelism, (2) speculative pipeline over layer-split nodes, which is the one that works on a bad network and aggregates RAM, (3) a dedicated drafter node, which mostly loses, (4) branch-parallel replicas, which saturate at about 1.2x, (5) hybrid grid, which loses on a good link. ### network-transport (HFT-style low-latency networking)
Main finding: the transport is a second-order lever, but it decides whether node count keeps paying. cluster_model.py (expert scheme + --dense-split + --overlap, 55 GFLOP/s, 16 GB, 192 messages/token = 2 barriers x 2 hops x 48 layers) gives, for single-stream tok/s at n=1/2/4/6/8 nodes: RTT 0.3 ms -> 4.58/6.61/11.07/14.27/~17; RTT 0.1 ms -> 4.58/7.57/14.05/19.66; RTT 0.01 ms -> 4.58/8.10/15.99/23.69/~31. Without dense split (the case in Playbook E.md, dense part stays on one master) the same 5 us link only gives 4.58/5.43/6.93/7.18 at 1/2/4/8 nodes, so the first lever is tensor-splitting attention + shared tensors, the second is the wire. Rule of thumb derived here: one-node layer compute is 218 ms/48 = 4.5 ms; with ideal split it is ~4.5/n ms; two barriers per layer should cost <= 15% of that, so (RTT + jitter) must be <= ~85 us at 4 nodes and <= ~42 us at 8 nodes. That is a 10s-of-microseconds budget, not an HFT 1-microsecond one, because CPU decode is slow: tuned Linux 2.5/10GbE with busy polling meets it, plain macOS TCP does not at >=4 nodes, and RDMA (ConnectX-3, ~$25-35 a card) buys headroom for 6-8 nodes. Where the model is wrong or optimistic: (1) dense_split assumes perfect tensor-parallel attention: nodes must divide the KV-head count (Distributed Llama restricts to 2^n nodes <= KV heads; our 125B head count is unknown to me, so 6 nodes may be impossible, use 4 or 8) and thin matvec slices run below 55 GFLOP/s per core; (2) it has no barrier jitter, I added 96 x jitter by hand (5 us RDMA spin, 20 us tuned Linux, 100 us macOS; all my estimates, not measured); (3) the net term is not overlapped even with --overlap; (4) the n=1 value is the overlap upper bound 4.58, while measured/projected single nodes are 2.2-2.5 (8 GB) to 3-4 (16 GB), so gains versus a real 8 GB node are larger (cache pooling is real, 8 GB x n), but this is hit-curve driven from a 30B trace; (5) 55 GFLOP/s is a Mac figure, a cheap x86 PC or N100 is unmeasured; (6) the straggler factor 1.27 is applied to the expert part only, fine for uniform routing, unmeasured for the 125B; (7) the model has no Linux-only effects such as IRQ coalescing, which can add 50-250 us if left at defaults. Nothing here needs quality loss: all schemes are exact (optional int8 activation transport is unmeasured). ### storage-scale-out
Verdict from cluster_model.py: storage scale-out alone cannot keep doubling tok/s. It scales only while the node is IO-bound. After that the 218 ms/token CPU term (12 GFLOP at 55 GFLOP/s) is a hard floor, and no extra disk bandwidth lowers it.

What it does well: pooling RAM and disks across nodes turns a disk-bound node into a compute-bound one. It is strongest with cheap, slow disks. With 8 GB RAM and a 0.5 GB/s disk, tok/s goes 0.87 (1 node), 3.6 (2), 5.5 (3), then flat near 6. That first step is about 4x per added node (the model's superlinear jump is a RAM-capacity effect: hit rate 0.56 to 0.80 to 0.89). After the ceiling it adds almost nothing: 5.83 (4), 6.19 (6).

With a fast 3.1 GB/s NVMe, 8 GB RAM (overlap on) gives 4.58, 4.96, 5.51, 5.83, 6.19, which is weak.

The model is optimistic in absolute terms. It gives 4.58 at 8 GB overlapped, while our projection for a single 8 GB node is 2.2-2.5, so scale every number by roughly 0.5. It also uses the 30B-trace hit curve. With --real-hit at 8 GB (3.1 GB/s NVMe) the curve is much worse: 4.26, 4.96, 5.51, 5.83, 6.04, 6.19, 6.30 (1 to 7 nodes), and the hit rate reaches only 0.77 at 4 nodes.

The only route to close-to-linear scaling is to also split the compute, which means a tensor-parallel dense part with fast low-latency links. That is not a storage idea, but storage sharding is its enabler: experts live where their bytes are, so no expert weights cross the network. With --dense-split, 8 GB RAM and 0.1 ms RTT / 1.1 GB/s, the model gives 4.58, 7.57, 10.9, 14.0, 16.9, 19.6 (1 to 6 nodes), about 1.6x per node near-linear. Also in that model: network time n is fixed per token (10 ms at 0.1 ms RTT, 36 ms at 0.3 ms, 55 ms at 0.5 ms). It ignores the growth of all-reduce and straggler cost with N and the fact that attention-head and KV splitting must divide evenly (llama.cpp has no tensor-parallel decode path for this). Treat the dense-split rows as an upper bound.

### replicas-and-hedging
Verdict for this lens: independent replicas or hedged copies of the same decode do NOT speed up one stream. This is the web-scale hedging lesson. Hedging cuts tail latency by spending duplicate work, and our token time is a mean, compute-bound at 55 GFLOP/s, so duplicates just burn cores. The replica idea works only if the nodes split the work of one verify step with a per-layer exchange, so the speculative positions run on different nodes at the same time.

Why the split matters (arithmetic): a single 16 GB node needs about 0.218 s compute plus about 0.1 s of reads per token. Verifying k draft tokens on one node costs about k times the compute (compute-bound CPU), so COMPARISON.md's k=4 speculation is only 0.74x to 1.09x. If k nodes each take ONE position and swap that layer's K/V (about 4 KB, estimated) once per layer, compute per step stays at about 1 token while the step yields 1 + accepted tokens.

Replicas do not give "double per node". Expected tokens per step is (1 - a^N)/(1 - a) for acceptance a and N positions. That is a saturating curve with a hard cap of 1/(1 - a), and it depends on the workload (prompt-lookup gains are weak on open-ended chat).

Simulation (my own, scratchpad file <scratch> estimate only, not measured): 48 layers, 4.54 ms compute per layer, 10 expert slots per layer with binomial misses at hit 0.77, 1 ms per miss (3 MB at 3.1 GB/s), 0.3 ms barrier per layer, max over nodes per layer. ## Prior art
Prior art says: single-stream decode scales well only with tensor parallelism over a very low-latency link, and only when per-token compute and memory bandwidth are the bottleneck and the model otherwise does not fit. Pipeline or layer split (llama.cpp RPC, exo pipeline, Petals, prima.cpp ring) gives about 1.0x or less per added node for decode; it buys capacity, not speed. The best evidence for 'add a node, get about 2x' is distributed-llama on Mac mini M4 Pro: 70B Q40 went 3.31 tok/s (2 nodes) to 6.51 (4 nodes) over Thunderbolt 5 and 3.25 to 6.04 over 10 GbE. The 1-node 70B point does not exist because it does not fit in 24 GB. For 8B (fits on one node) the scaling was 16.91, 30.27, 38.83 tok/s, i.e. 1.79x then 2.3x at 4 nodes (about 58% efficiency). That is a dense model, fast link, and a compute/bandwidth-bound regime. Exo with RDMA over Thunderbolt 5 (macOS 26.2+, M4 Pro/Max and M3 Ultra only, nodes must be fully meshed) reports 1.8x at 2 and 3.2x at 4 nodes (README claim, no methodology), but on $10k+ Mac Studios. The only MoE-on-cheap-hardware number found: distributed-llama, Qwen3-30B-A3B Q40 on 4 x Raspberry Pi 5 8 GB over a gigabit-class switch, 13.04 tok/s prediction, with sync 15-40 ms/token typical and up to 94 ms; no 1/2-node baseline exists because it does not fit in one Pi. No source found demonstrates expert-parallel decode across multiple cheap CPU nodes with node-count scaling for a ~100B+ MoE; this is a gap, not evidence either way. Honest reading for the 125B target: (a) the 'double with each node' result only holds when tensor parallelism splits the dense part too and the link has RTT of tens of microseconds to ~1 ms; (b) with 48 layers and about 2 syncs per layer in dllama-style TP, that is about 96-160 syncs/token, so at 0.3 ms LAN RTT the sync floor is roughly 30-50 ms/token, and at 1-3 ms Wi-Fi it is 100-500 ms/token (arithmetic from the numbers above, estimate); (c) pipeline-style splits cannot beat the single-node compute ceiling for one stream. The most credible cheap path is TP over the dense part with per-node RAM that holds a shard of the 69 GB (so disk reads disappear), over wired gigabit or better, with the mini-Mac Thunderbolt/10GbE options as the premium variant. ## Hardware and prices
Short answer: no cheap-node cluster doubles single-stream tok/s per added node, and I found no configuration that does. Gains are real but come in two regimes. (a) Expert sharding alone (what llama.cpp RPC-style splits can do) gives about 1.5-1.8x at 2 nodes, flattening at about 2.5x by 6 nodes. Most of that gain is the aggregate RAM cache, not compute, because the dense part (57% of FLOPs) stays on one master. (b) Only if the dense part is also tensor-parallel (model flag dense_split, 192 small messages per token) does it get near-linear: 2.1x at 2 nodes, 4.3-4.8x at 4, 6.4x at 6 for N305-class nodes at 2.5GbE. That is a model upper bound; llama.cpp has no such mode, so it needs custom code, and it is very sensitive to per-message latency (N305, 4 nodes, 2.5GbE: 11.8 tok/s at 0.2 ms RTT, 8.8 at 0.5 ms, 6.2 at 1.0 ms). USB 2.5GbE adapters through a switch with TCP are unlikely to be better than about 0.3-0.5 ms RTT, so treat dsplit figures as optimistic by roughly 25-40%.

## Model audit
Pure layer-split (pipeline, which is what llama.cpp RPC does) does NOT scale single-stream speed. It stays near 4.5 tok/s on laptop-class nodes because layers remain sequential. It only helps when you are I/O-bound (about 1.1x at 16 GB; up to 2.4x for 3x-faster nodes, because the pooled cache removes disk misses). The only design where each added node gives a large gain is expert-parallel combined with a tensor-parallel dense part, with the router replicated and 2 all-to-all exchanges per layer. In my corrected model, 16 GB laptop-class nodes on 10GbE go 4.1 (1 node) to 6.6 (2) to 8.8 (3) to 10.5 (4) tok/s. A node 2 gives about 1.6x, not 2x. Efficiency then falls (about 1.3x going from 2 to 3 nodes and 1.2x from 3 to 4) and tok/s saturates near 12-14 at 6-8 nodes. The bounds that stop scaling, in order: (1) the 2-node jump is capped by the straggler (1.24 at 2 nodes, 1.67 at 4, 2.4 at 8) and by dense tensor-parallel efficiency; (2) per-layer network latency, 48 layers x 2 exchanges, about 18-36 ms per token at 4 nodes; (3) disk I/O disappears once the pooled cache is above about 60% of the experts. If the dense part stays on a master (no tensor parallel), tok/s saturates at about 5-6 whatever the network, because 57% of the FLOPs are serial (Amdahl). Pure gains from 2 to 4 nodes are therefore real only with custom software (expert-parallel plus tensor-parallel dense) that does not exist off the shelf. Budget: 4 used 16 GB M1/M2 minis cost about $1.8-2.6k, which is over a few hundred dollars. 4 N100 boxes (about $100-170 each, 1GbE or 2.5GbE only) cost about $400-700 and reach about 5.0-5.2 tok/s at 4 nodes in the model. Everything here is arithmetic on estimated inputs, not measurement; a hands-on test of 2 nodes with real round-trip times is the cheapest way to check it.
Errors found:
- E1 straggler: constant 1.27 is the measured 2-node value only (E.md: 1.266 measured, 1.244 exact uniform for k=10 of 512). Monte Carlo for 10 of 512 uniform placement gives 1.24 / 1.47 / 1.67 / 2.05 / 2.41 at n = 2 / 3 / 4 / 6 / 8. The old model overstates expert-compute scaling for n>2 (4-node expert compute is 1.67x the mean, not 1.27x). Misses also straggle per layer (max over nodes of miss reads), which the old model ignored.
- E2 cache accounting: for the expert scheme the old code charges the full 1.9 GB dense part to EVERY node (cache_node = ram - reserve - DENSE_GB), but only the master (or 1/n each with dense split) holds it. Aggregate cache should be n*(ram-reserve) - dense - kv in both pipeline and expert schemes; the old pipeline was right, the old expert scheme under-counted by (n-1)*1.9 GB (5.7 GB of 37 GB at n=4).
- E3 hit curve: default used the 30B-trace curve in 30B footprints for a 512-expert model. That gives hit 0.95 with only about 15% of experts cached at 16 GB; the project's own real-model curve gives about 0.77 (single node 3.2 tok/s serial, not 4.19). Fixed: real curve is the default. The curve is itself an unverified public number.
- E4 dense split message count: old model charges 2 extra messages per layer (4 total) for tensor-parallel dense. If every node runs the tiny router itself (replicated), a layer needs only 2 all-to-all exchanges (attention all-reduce, then expert-partial all-reduce), the same 2 one-way latencies as the master scatter/gather. So dense split costs almost no extra latency but needs a switch or full mesh (Thunderbolt Macs have 2-4 ports so only rings/stars), and each exchange moves (n-1) copies. The old 4-step form is kept as 'star'.
- E5 master NIC bytes: old model charges one activation copy per step regardless of n; the master (or every node in all-to-all) sends/receives (n-1) copies. Negligible at 4 KB on 10GbE, about 0.1 ms per step on 1GbE at n=4. Also, 4 KB assumes hidden 2048 fp16 (30B proxy); the 125B hidden size is not in the files, and fp32 partial sums would be 8 KB (checked: 4 nodes 1GbE TP 8.8 -> 8.1 tok/s).
- E6 serial vs overlap: old overlap = max(comp, io) over the whole token is an ideal bound that needs perfect cross-layer prefetch (ANGLE_SWEEP: router needs the attention output, so only the same layer's expert-compute window can hide reads; measured-style overlap gains are 1.27-1.33x). Fixed: serial, 'window' (realistic bound) and 'ideal' (old) modes. Network is always on the critical path (dependency chain per layer), which the old model had right.
- E7 no software overhead: old model had zero per-exchange software cost (thread wake, syscall, ggml barrier) and perfect tensor-parallel efficiency. Added sw_us=100 us per one-way exchange and tp_eff=0.85 (both estimates). A 3x jitter on RTT cuts 4-node 1GbE TP from 8.8 to 6.8 tok/s and 10GbE from 10.5 to 9.1.
- E8 pipeline: model is right that compute does not shrink and only aggregate cache helps, but it also ignores that pipeline could serve n concurrent streams (not the user's goal) and that llama.cpp RPC is layer-split, so it is the ONLY scheme with ready software, and it is the one that does not scale.
- E9 KV cache: not modelled; it lives with its layers in pipeline (split 1/n) and on the master in expert-parallel without a dense split (sharded by heads with dense TP). The reserve (4.95 GB) is assumed to cover it; kv_gb parameter added (default 0); 125B KV size unknown, so long contexts would eat expert cache and are unmodelled.
- E10 router ordering: confirmed router must run on the master/replicated before the scatter (needs attention output); old model implicitly assumed this, but nothing in it prevents cross-layer prediction; no change to the arithmetic, noted as the reason for the 'window' overlap mode.
- E11 prefill ignored: old model decode only. Added prefill_tok_s (512-token chunks, compute-bound, whole expert set streamed per chunk, pf_mult=1.0 pessimistic). Prefill scales with nodes: laptop 3.9 tok/s single; 4 nodes about 17-18 tok/s (10GbE TP, or pipelined chunks), but 1GbE expert-parallel prefill is only 6.3 because 512 x 4 KB activations per layer saturate the link.
- E12 dense share: 57% is by parameter count (3.4 of 6 B), an estimate not a measurement. It also treats FLOP/s as the limit; at batch 1 CPU decode is largely memory-bandwidth bound (55 GFLOP/s is about 15 GB/s of weights), so the '3x GFLOP/s' scenario is only valid if the node's weight-streaming bandwidth is also 3x; an M-series mini's bandwidth is far higher but its NEON CPU kernel rate is unmeasured here.
